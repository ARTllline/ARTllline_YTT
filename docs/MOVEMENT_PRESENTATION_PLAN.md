# Плавное движение и обзор: проверка контракта и план

11 ноября 2026. Статус: **согласован пользователем, реализован**.
Предыдущие локальные изменения аудита производительности сохранены.
Результаты и ограничения: [MOVEMENT_PRESENTATION_RESULTS.md](MOVEMENT_PRESENTATION_RESULTS.md).

Уточнения параметров после реализации: batch/credit ≤126 units; локальная очередь
ограничена двумя batches (251,8 units: отправленный и ещё не отправленный), как
прежний предел из двух шагов. Это позволяет выдерживать измеренный полный HTTP
цикл около 450–500 мс. Credit остаётся только серверным, timeout — 900 мс.
Receipt дополнен `acceptedDistance`: сервер принимает только доступный по времени
префикс, а клиент сохраняет остаток со всеми углами и разворотами. Коллизия в
принимаемом префиксе отвергает операцию целиком, без расхода credit/sequence.

## Предлагаемый минимальный объём

### 1. Ограниченное пакетирование prediction

Сохранить существующие endpoints, один in-flight запрос, интервал отправки не чаще
200 мс, campaign/scene locks, idempotency, stream/sequence/origin и полную серверную
проверку маршрута. Не вводить отдельный transport или серверный игровой ticker.

Расширить control receipt серверными `streamId`, `acceptedSequence`,
`position`, `remainingCredit`, `maxBatchDistance`. Поля авторитетного результата
не заменяют существующие revision/mutationId и player-specific projection.
Новый start/receipt capability отделяет новую реализацию от старой: без capability
клиент использует старые пределы. DTO не содержит геометрии.

Предлагаемый начальный предел batch/prediction — до 700 мс движения (126 units при
180 units/s), с жёстким количеством waypoints и текущими server-side collision
checks. Это параметр для измерения, не доказанная оптимальная величина.
Credit начисляется только по серверному времени и ограничивается тем же пределом;
restart/retry не создают credit. Клиент использует выданный credit консервативно.
Увеличение максимального batch не означает увеличение скорости или права проходить
сквозь препятствия. Если обработка+RTT превышают предел, безопасная остановка
предпочтительнее неограниченного расхождения.

Локально хранить bounded очередь ещё не принятых samples ввода. На receipt удалить
только подтверждённый batch, привязать остаток к canonical origin и переиграть
допустимую prediction. На принятии собственного batch не сбрасывать presentation
в его старую конечную точку. Малые безопасные поправки сглаживать; при неизвестном
препятствии, teleport или потере авторитета сбросить prediction, не интерполировать
произвольный путь сквозь стены. Snapshot и gameplay state остаются canonical.

### 2. Drag: один commit, отдельный playback

Сохранить единый атомарный commit полного drag-маршрута и однократные budget/triggers.
Явно отделить request-параметр presentation от `routeStep` и `instant`; сервер
возвращает accepted path с рассчитанной длительностью для normal movement.
GM teleport/edit сохраняют мгновенную семантику. Пока receipt не получен, показывать
локальный ghost/destination, не объявляя неподтверждённый путь разрешённым.

Для показа принятого пути переиспользовать `TokenLayer` и существующий ticker,
одинаково для Player и GM. Esc прекращает локальное продолжение/ещё не отправленные
команды. Уже совершённый атомарный commit Esc не откатывает; сетевой abort также
не означает серверную отмену. Остановка canonical координат посреди принятого drag
потребовала бы отдельного domain-протокола и в этот минимум не входит.

### 3. Обзор: консервативная визуализация

Для минимального варианта **не расширять право игрока на информацию**:

- exact currentMask, entity filtering, manual cover и explored progression остаются
  серверными;
- визуальный индикатор радиуса следует presentation-позиции каждый кадр, но вся
  его подсветка клипуется последней действительной авторитетной маской;
- переход к вновь полученной маске воспроизводится по presentation clock с
  ограниченной длительностью, без пересоздания Graphics/RenderTexture каждый кадр;
- revoke, изменение сцены/прав, snapshot reset немедленно отменяют старые transitions;
  старые receipt не могут восстановить отозванную видимость;
- окружность-индикатор, shader transition и реальные изменения разрешённой области
  измеряются отдельно. Анимацию индикатора нельзя выдавать за 60 новых LOS-расчётов/с.

**Граница гарантии:** новые участки карты по-прежнему открываются только после
серверного разрешения. Вблизи границы LOS нельзя обещать точный обзор, непрерывно
следующий за predicted героем, при отсутствии новых авторитетных данных. Плавное
движение героя не требует и не даёт prediction видимости.

### 4. Ошибки и повторная синхронизация

| Событие                                        | Поведение                                                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Rejection / скрытая коллизия                   | Остановить prediction, выбросить неподтверждённые samples, восстановить canonical; не раскрывать причину/геометрию блокировки        |
| Timeout                                        | Результат считается неизвестным, новый stream не запускать до восстановления snapshot/подтверждения; не повторять с новым mutationId |
| HTTP/Echo duplicate или reorder                | Сопоставлять stream+sequence+mutationId, применять canonical один раз; visibility revision имеет отдельный барьер revoke             |
| Keyup / Esc                                    | Немедленно прекратить новый локальный ввод; явно различать drain уже отправленного batch и отмену ещё не отправленных samples        |
| Дверь, препятствие, внешний move, combat start | Инвалидировать неподтверждённый маршрут; следующий шаг заново проходит текущие серверные проверки                                    |
| Disconnect / reconnect                         | Остановить prediction и transitions, snapshot → hydrate → subscribe; старые samples/stream не воспроизводить                         |
| Editor / teleport                              | Сохранить существующие мгновенные editor transforms и серверные проверки, не применять игровой playback                              |

## Что потребует отдельного расширения безопасности

Если требуется не ограниченный авторитетной маской индикатор, а **точная видимость
вдоль всей анимированной траектории**, текущего контракта недостаточно.
Возможный следующий вариант — серверные per-player masks для промежуточных точек
уже принятого маршрута с привязкой к revision/path distance. Нельзя просто прислать
их и назвать безопасными: промежуточная область может отсутствовать в конечной
маске, и сам payload уже раскрывает информацию независимо от момента её показа.

Для такого варианта сначала требуется согласовать право на информацию вдоль
пройденного пути, поведение explored memory, doors/revocations и бюджет CPU/payload.
Нельзя передавать будущие entity DTO с расчётом скрыть их до нужного кадра. Вариант
с выдачей геометрии/LOS для неподтверждённого движения исключён. Этот дополнительный
контракт в рекомендуемый минимальный этап не входит.

## Проверка после согласования

1. Новая paired baseline на Scene 10 «Лесная таверна»: production build, одинаковые
   camera/viewport/визуальные настройки, GM + Player в независимых contexts.
   Нулевой added RTT, затем добавочные 100/175/250 мс (отдельно фиксировать фактический
   RTT с server time). HTTP задержка и отдельный тест задержки Echo, без повышения
   частоты запросов. Минимум 10 повторов и длинное удержание WASD 10–15 с, чтобы
   начальная prediction не скрывала накопление backlog.
2. WASD: старт/keyup, поворот и реверс, стена/закрытая дверь; drag полный путь вокруг
   препятствия, повторный drag, Esc до/после отправки, combat budget и triggers.
3. Rejection, dropped response после commit, duplicate/reorder, reconnect,
   внешний move и изменение геометрии. Проверять позиции в БД и у GM, отсутствие
   двойных triggers/budget и сохранение secret filtering.
4. Таблица до/после: input→первый visual frame p50/p95, скорость/длина за фиксированное
   время, p95/max неподвижных интервалов при удержании, correction distance, очередь,
   частота visual circle/transition и отдельно authoritative masks, FPS/frame p95,
   long tasks, HTTP count, server CPU и payload bytes. Отдельно фиксировать
   presentation-to-authority separation и время convergence после keyup.
5. Целевой p95 frame ≤16,7 мс; локальная реакция — ближайший доступный кадр;
   bounded очередь, отсутствие необъяснимого отката на каждом receipt; сходимость
   после последнего принятого ввода. Нулевая новая неавторизованная видимость —
   обязательный инвариант, а не статистический показатель.
6. Fixture backup/restore как в предыдущем аудите, без новых аккаунтов/сцен.
   Тесты — SQLite in-memory и целевые Vitest. Сравнение выполнять до изменений
   и после них, не заменять новыми результатами прежние артефакты аудита.

## Решение для согласования

Рекомендуется реализовать пункты 1–4: ограниченные batches при прежней HTTP-частоте,
reconciliation, атомарный drag с playback, плавный **консервативный** обзор внутри
полученного разрешения. Право на новые области не предсказывается. Изменяется
контракт control receipt/batch и drag presentation; модель секретности сохраняется.

Если обязательна точная маска на всей predicted траектории без ожидания сервера,
этот объём не удовлетворит требование: сначала нужно отдельно согласовать иной
контракт авторизации, а не скрывать ограничение визуальным эффектом.
