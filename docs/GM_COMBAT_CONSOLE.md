# Task 31 — GM Combat Console

Локальная реализация 2026-10-30. Существующий правый dock стал runtime-пультом:
карта остаётся основной рабочей поверхностью. Новых зависимостей, миграций,
аккаунтов, кампаний, сцен и игровых сессий нет.

## Архитектура

`CombatPanel` объединяет инициативу, закреплённый текущий ход/раунд, runtime-карточку
участника, `CombatActorControls`, `TokenCombatControls`, `GMQuickCheck`,
`GMResolutionQueue` и `CombatHistory`. При начале/перезагрузке активного боя GM dock
открывается автоматически, если нет незавершённого редактирования. Выбранный участник
может отличаться от текущего; новый ход возвращает контекст к текущему участнику.
Камера меняется только явной кнопкой «Фокус».

Авторинг standalone NPC сохранён в Inspector (`CombatProfileEditor`); описание
правил и выбор runtime-действия больше не открывают редактор NPC. Кампанийные NPC
используют способности своего Character, standalone — свои Token abilities.

## Ходы, NPC и коррекции

Большая закреплённая «Следующий ход»: один клик или N. Shift+N вызывает существующий
Previous; это настоящие границы end/start, а не откат времени. Новый раунд начинается
при обходе порядка. Постоянно видны раунд, текущий участник и позиция хода.
Alt+H фокусирует HP, Alt+C — поиск состояния. Повтор клавиши, ввод в полях,
диалоги, targeting и незавершённая SaveQueue блокируют горячие команды. Подсказки
есть в tooltip и общей справке клавиш. Player этих команд не получает.

NPC: кнопка атаки → существующий `AbilityTargeting` на карте → тот же `AbilityActions`
и `CombatExecution`. Если подходящая цель уже выбрана на карте, достаточно кнопки
атаки. Та же геометрия и та же серверная проверка дальности. Действие/бонус/реакция,
оставшееся движение и причина блокировки видны в карточке. Обычный drag расходует
существующий `TurnBudget`, включая Prone; нового GM movement engine нет.

HP: урон, лечение, подписанный Enter, точная установка HP с сохранением temporary HP.
Установка 0 HP завершает концентрацию. Канонические состояния берутся из установленного
Compendium: быстрые карточки, поиск, длительность, раунды, источник и видимость.
После применения picker закрывается. Строки показывают HP/AC/инициативу, состояния,
0 HP и недееспособность; tooltip содержит каноническое описание и срок.

Коррекции Action/Bonus/Reaction и потраченного перемещения находятся в компактном
раскрытии runtime-карточки. Все эти изменения авторизует сервер, публикует realtime
и записывает как GM override. Существующие UUID receipts защищают повтор запроса.

`GMCorrections` пишет before/after в `combat_events`. Отмена доступна только для
последней ручной HP/condition-коррекции активного боя, при той же ревизии сцены и
совпадении текущего состояния с after. Изменившиеся managed effects/концентрация
делают коррекцию необратимой. Никакого отката атак, заклинаний, ресурсов или добычи.
Отмена сама журналируется. JSON-объекты сравниваются по значениям: MySQL сортирует
ключи, что отдельно воспроизведено и защищено тестом.

## Журнал и результаты

Журнал последнего боя: до 100 структурированных событий, обновление по ревизии
сцены при открытом журнале; без постоянного polling. Обычный фильтр скрывает
низкоуровневые movement/action-spent и дублирующие roll/damage события. Есть Бой,
Броски, HP, Состояния, Система. Читаемые строки объясняют попадание/промах, Сл/AC,
урон/лечение, смену раунда, истечение состояния и коррекции ГМ.

Раскрытие показывает исходные кости, модификаторы, причины преимущества/помехи,
бонусные кости эффектов, источник Сл, типы урона, сопротивление/иммунитет/уязвимость.
`ability.resolved` ссылается на durable execution и сохраняет структурированный
результат. Таблица по целям содержит save/Сл, успех, тип/размер урона и исторические
HP before/after; она не подставляет текущие HP вместо результата того события.

Журнал и новый `/scenes/{scene}/combat/session` — только GM. Полные результаты
сохраняются сервером; Player presenter удаляет GM context, итоговую ручную заметку,
исторические NPC HP, детали защиты и private save provenance. Realtime использует
существующий recipient-safe ScenePublisher; очередь и заметки не публикуются игрокам.

## Ручное разрешение

`GMResolutions` — проекция существующего `AbilityExecution`, а не workflow engine.
Сценическая очередь выбирает все pending casts своего campaign/scene (не последние
100, которые могли бы потерять старые незакрытые задачи). В результате хранятся
источник/кастер/цели, coverage, неизменяемый контекст описания и причины ручного шага,
уже выполненные броски/последствия, затем статус/GM/user/time/note.

PARTIAL/MANUAL создают pending после принятого casts; проваленный scroll check не
создаёт несуществующую работу. Очередь доступна и вне активного боя. До трёх задач
видны сразу; длинная очередь компактно сворачивается. Задача → результаты/описание →
ручные HP/condition primitives для цели либо выбранного на карте Token → заметка →
«Шаг выполнен» / «Закрыть без эффекта». Дополнительные последствия не применяются
самим закрытием. Coverage не меняется. Старые spellcasting controls закрывают ту же
задачу через тот же сервис. Перезагрузка восстанавливает очередь; повтор/конкурирующее
закрытие идемпотентны либо дают явный conflict.

`qa:townhouse` закрывает старые pending этого QA-сценария как `dismissed_by_qa_reset`,
не удаляя executions и историю. Обычное завершение боя не закрывает незавершённые
ручные задачи автоматически.

## Быстрые проверки

Текущий участник либо выделение на карте → save/check → необязательная Сл.
DEX/WIS/CON saves, Perception, Athletics и собственный ключ существующей проверки.
`GMSessionChecks` вызывает `CombatStats` / `TokenCheckStats`, `ConditionRules` и тот же
`CombatExecution::roll`; модификатор не присылается клиентом. Пакет до 40 участников
проверяется атомарно. Без Сл нет выдуманного pass/fail. По умолчанию результат private;
public может показать только итог, Сл показывается отдельно и только по выбору GM.
Скрытые Token исключаются из player feedback сервером.

## Скорость за столом

Оценка «до» по прежним контролам; «после» проверено native Chromium UI.
Редактирование числа считается одним действием, прокрутка не включена.

| Операция                                  |                             До |                                                 После |
| ----------------------------------------- | -----------------------------: | ----------------------------------------------------: |
| Следующий ход                             |            1 + поиск/прокрутка |                            1 / N, закреплённая кнопка |
| NPC basic attack, текущий участник        |                        около 5 |              2: карточка → карта; 1 с выбранной целью |
| Каноническое состояние, текущий/выбранный |                        около 4 |          2; дополнительные настройки по необходимости |
| HP correction, текущий/выбранный          |                            2–3 |                           2: число → урон/лечение/set |
| Ручной шаг                                | около 5–7 и переход в авторинг | 2: задача → закрыть; +1 для свёрнутой длинной очереди |
| Отмена последней безопасной коррекции     |                  отсутствовала |                                                     1 |

## Задержки и целевое исправление

Нативный первый прогон выявил p95 Next Turn 1.211 s. Контролируемый профиль того же
перехода с обязательным rollback показал 1434 SQL: 620 одинаковых чтений active
spell effects и 618 повторных Character→Token lookups. Это происходило при сборке
производных полей/DTO, включая наличие/отсутствие эффектов, а не при самом броске.

`SpellEffects::project` повторно использует effects/token IDs только внутри одного
read-only DTO (`CharacterActions::projection`, `SceneSnapshotBuilder::token`).
Вложенное чтение разделяет этот снимок; `finally` очищает его даже при исключении.
Между командами/изменением эффекта кэша нет. Empty effects не запрашивают token IDs.
Это scoped PHP service, не Redis/долгоживущий кэш и не новый слой gameplay state.

Три одинаковых rollback-профиля до/после на подготовленном MySQL-сценарии:

| Метрика                |       До |    После |
| ---------------------- | -------: | -------: |
| SQL / Next Turn        |     1434 |      229 |
| Медиана сборки команды | 652.1 ms | 145.1 ms |
| Медиана времени SQL    | 387.6 ms |  65.8 ms |

Нативные Chromium-запросы (локальные небольшие выборки, не WAN/load test):

| Операция          |        До, median / p95 |    После, median / p95 |
| ----------------- | ----------------------: | ---------------------: |
| Next Turn         | 774.4 / 1211.1 ms, n=12 | 191.6 / 232.7 ms, n=18 |
| Ability execution |   642.5 / 721.4 ms, n=3 |  176.1 / 217.7 ms, n=3 |
| Condition apply   |   340.6 / 500.1 ms, n=3 |  113.2 / 116.3 ms, n=2 |

HP delta: 961.1 → 227.9 ms (по одному UI-запросу, малая выборка).
Точная установка HP после исправления: 137.3 ms (n=1). Это другой primitive,
поэтому не выдаётся за before/after сравнение с HP delta. Ручное закрытие без
дополнительных последствий было порядка десятков миллисекунд; undo отдельно
публикует изменившийся Token/Character и занимает больше времени.

rAF p95 исходного slice ~8.4 ms; три клиента финального прогона — 8.4 ms, по одному
canvas. Нет измеримого практического ухудшения рендеринга. После оптимизации
повторены полный combat loop и native concentration: Shield of Faith немедленно
меняет AC 18→20, добровольное прекращение немедленно возвращает 18.

## Проверки

- Backend: **251 tests / 3763 assertions**, зелёные, disposable SQLite/temp storage.
  Включают 15 новых GM-console/performance regressions: права и role-revoked replay,
  HP/conditions/undo, MySQL JSON ordering, границы срока, manual lifecycle/reconnect,
  UUID/scene scope, private/batch checks, redaction заметок/NPC HP, концентрацию,
  ограничение числа projection SQL и очистку кэша после исключения/изменения.
- Frontend: **202 tests / 43 files**, зелёные. Восемь новых console tests плюс
  обновлённая проверка linked NPC runtime actions; остальная Player RPG suite сохранена.
- TypeScript, ESLint, production Vite build, Pint **19 PHP files**, `git diff --check`
  прошли. Docker doctor выполнен после финального reset.
- Горячие клавиши, batch saves, log filters/expansion, correction undo, reconnect,
  realtime/privacy и фактические click flows дополнительно проверены в Chromium.

## Приёмка и пределы

Использован только постоянный Flinns Townhouse, campaign 5 / scene 5 / session 1,
существующий GM и Players 2/8 в трёх изолированных контекстах. Старт из reset,
несколько ходов/четыре раунда, Player attack, NPC Shortbow через карту, movement,
HP correction/undo, canonical conditions, Player Fireball III с тремя целями,
таблица результатов, закрытие PARTIAL, истечение timed condition, secret batch DEX
save, горячие клавиши/защита ввода, reconnect pending queue, runtime Action override,
Player DTO/realtime privacy. Полные NPC/Spell editors в игровой петле не открывались.

Chromium desktop 1440×1000, GM tablet 900×1000 и Player 390×844; JS errors отсутствуют, mobile page overflow
не обнаружен. Это viewport-проверка, не Safari/Firefox/физический телефон/WAN.
После приёмки сценарий возвращён в подготовленное состояние `qa:townhouse`.
Игнорируемые доказательства и замеры: `artifacts/task31-gm-console/`.
